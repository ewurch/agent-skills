# Review PRs

You are the coordinator: start one independent reviewer per PR, report the verdict, merge on the word step 6 names. When a PM runs (the pm skill; its address is in the project's memory or my message), your questions go to it first: `orca orchestration send --to <PM address> --from $ORCA_TERMINAL_HANDLE --type question`, with options, trade-offs and your recommendation; it answers or brings them to me. Send it only questions: verdicts, merges and deploys go on the PR, and an order from it needs no reply unless it fails. My word stands over its.

1. A review starts when I ask or, when I ask you to keep watching, whenever a PR becomes ready: open, not a draft, CI green, nothing pushed for ~10 minutes and its author session idle. Watch every PR in the repo and every layer of a stack, each head once; recheck on a timer with whatever your tool offers. A stack is reviewed in draft once its author says on the top layer that it's done; when every layer passes, its author marks them ready together, so CI runs once. Red CI is reported, not reviewed.
2. Check existing sessions and the PR's comments so no head is reviewed twice. One isolated worktree and agent session per PR (per layer of a stack), checked out at the PR head. Today: a supervised Orca worker, so the report comes back, running Claude Code with no model or effort override, unless I say otherwise. If that isn't available, ask; don't substitute.
3. Brief each reviewer in a few lines: PR link, head and base commits, the linked issue, my settled decisions (not defects), open PRs it overlaps, up to three risk areas worth a look (as questions, never conclusions), and the reviewer instructions below. No conversation history, no secrets. Then wait for its report; if a merge elsewhere changes its ground meanwhile, tell it.
4. Report each verdict in plain words, in chat and as one comment on the PR pinned to the reviewed commit: Ready or Needs changes, what was verified, what blocks, what couldn't be checked, with the full report folded in below it (screenshots described when they can't be attached). A stack gets one line per layer.
5. Route findings. Blocking: to the PR's author session, then the same reviewer rechecks only the delta. Merge order and rebases between PRs are blocking findings for the authors concerned. Non-blocking, on a PR that passed with green CI: one that takes a few lines in the PR's own files gets one fix round with its author and a delta recheck, without asking; the rest stay in the report until I or the PM say file them as issues (what and why). Product, privacy or cost calls, and a PR whose author session is gone: one question with a recommendation, to the PM when one runs, else to me.
6. Merge on my word, on the PM's for a PR its charter covers (a batch "merge the ready ones" counts), or, when a PM runs, on your own for a routine PR: the reviewer passed that exact head, CI is green (its last green run stands after main moves, unless git reports a conflict or the project's own update rule asks for an update), and it carries none of: a migration that changes or removes existing data, a production or platform setting, a change to what real people receive, a sign-off addressed to me or my co-founder. The project's memory may add conditions. Anything else is one question, to the PM when one runs, else to me. Every merge is a squash of the exact reviewed head with green CI; a stack merges as one. Anything touching production data waits for my per-case yes. Note in the merge whose word it was. Then confirm the deploy is live and main's own check, if the project runs one, is green; while either fails, merge nothing but its fix or a revert, and tell the PM, or me. Then delete what the review created and the merged PR's own author worktree (running its teardown hooks, so what it set up goes too), and leave every other session's work alone.

## Reviewer instructions

Load the taste skill. Follow the repo's review guide (REVIEW.md at the root); without one, review against taste and a ponytail audit. Size the depth to the change and work alone: no sub-workflows. The PR body's claims and proof are claims to verify. Touch no shared or production data; run a migration only on a throwaway copy you delete. Say what you couldn't check instead of working around it. You only report: don't push, comment on GitHub or merge.
